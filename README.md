# userd

BORUIX 的**账户守护进程**：把账户表里登记的用户，变成文件系统里真实存在的家目录。

[English](README.en.md)

## 它做什么

```
[userd] users.json loaded: 3 account(s)
[userd] /users/alice: created (uid=1000 gid=1000 mode=0700)
```

| 工作 | 内容 |
| --- | --- |
| 建家目录 | 为每个账户创建 `/users/<用户名>` |
| 设归属 | 目录所有者设为该用户，权限设为"仅本人" |
| 放身份投影 | 在目录内写入一份自解释的身份信息（用户 ID、组 ID、用户名） |

第三项是**只读投影**——放在用户自己的目录里，谁都能看懂，但不由用户修改。

## 内核不解析账户表

账户表是**普通文件**，内核既不解析它，也不认识"用户"这个概念。创建目录、设置权限全部在用户态用
普通文件操作完成——**没有为此新增任何系统调用**。

价值在于**可替换性**：账户数据长什么样、放在哪里、用什么格式都是用户态的事。换个账户方案不需要
动内核；内核只提供通用的文件与权限机制，不掺和账户策略。

## 反复执行不会出问题

本进程周期性重新检查账户表。这要求每项操作都**幂等**：

| 情况 | 处理 |
| --- | --- |
| 家目录已存在 | 正常，继续 |
| 身份信息内容没变 | **不重写** |

第二条尤其重要。每次巡检都无脑重写会产生持续的无效写入——每一次都要经过文件系统、更新元数据、
产生日志。**判断"内容是否真的变了"再决定写不写**，省掉无用功，也让日志里只出现真正的变化。

## 表里删掉一个账户会怎样

**家目录不会被删除。**

这是刻意的数据安全决定：**"删除账户"和"删除数据"不是一回事**。管理员把一个用户从账户表移除，
意图通常是"这个人不能再登录了"，而不是"把这个人的所有文件都销毁"。

两者若实现成同一件事，后果不可逆——一次误操作就永久删除一整个用户的数据。

所以本进程只做**增量补齐**：新增的账户补建家目录，移除的账户**保持原样**。清理数据属于专门的
管理工具，不该由一个自动巡检的守护进程顺手做掉。

## 账户表异常时

| 情况 | 行为 |
| --- | --- |
| 表不存在 | 如实记录，继续驻留等待 |
| 文件不是合法文本 / JSON 格式错误 | 如实记录，跳过 |
| 某一条记录缺字段或数值非法 | **只跳过这一条**，其余正常处理 |

**绝不伪造一个空账户来充数**。最后一条也值得说明：账户表是用户态文件，**内容不可信**，一条畸形
记录不应该让整个程序崩溃，也不该影响其他正常账户。

## 启动失败不是致命的

本进程由系统初始化进程拉起。**启动失败系统仍然可用**，只是没有家目录。账户服务是锦上添花，不是
没有它就活不了——不制造"半个系统能用"这种说不清的状态。

## 构建

```bash
cargo build --release
```

## 文件结构

```
userd/
├── Cargo.toml    # 包定义
├── build.rs      # 注入链接脚本
├── linker.ld     # 用户态段布局
└── src/
    └── main.rs   # 账户同步与巡检循环
```
